# Candidate search

`candidate.search` is a READ operation for bounded retrieval of recorded candidate proposals. It is available through the Core catalogue, CLI, and stdio MCP server. It does not promote proposals. A hit is marked canonical only when the verified canon reader has a promoted assertion with the same candidate id **and** content version.

Configure `NOUS_OS_CANDIDATE_STORE_PATH` and `NOUS_OS_CANDIDATE_REPLACEMENTS_PATH`. The replacement manifest is a read-only JSONL file with `old` and `new` proposal ids on each row. It is maintained by the review process; search never writes it. Set `NOUS_OS_CANON_ROOT_PATH` to enable the exact promoted-assertion join. `ranking="source_semantic"` also needs an existing semantic index. No search request rebuilds that dense index.

The request takes `query` (required), `limit` (1–20, default 10), an opaque `cursor`, `include_replaced` (default false), and `ranking` (`text` or `source_semantic`). Queries contain plain words and double-quoted phrases. Every term is escaped as a literal FTS phrase, so supplied operators do not change query syntax. Text ranking uses BM25 over statements, cited spans, content scope, and bounded `scope:` note tags. Cited spans are decoded from JSON and normalized before indexing. Semantic ranking uses the rank of cited **sources**, not similarity to candidate statements; each such hit states `semantic_basis: "cited_source_rank"`.

The response includes `store_generation`, `total_matched`, `replaced_excluded`, `replaced_unreadable`, `hits`, and `next_cursor`. `replaced_excluded` counts readable replaced versions matching this query but omitted when `include_replaced=false` (zero when true). `replaced_unreadable` counts replaced versions in the store refused by the review model and omitted regardless of `include_replaced`; they cannot be returned even when it is true. A refused version is omitted only when its proposal id is a manifest `old` or a `supersedes` target. A refused live version makes the whole request fail with `CandidateStoreUnreadable`. Each hit includes the proposal content, citations, exact canon standing, a conservative epistemic label, and replacement status. Non-canonical hits say “Recorded candidate proposal” and have `is_asserted: false`. Canonical hits say “Promoted canonical assertion” and have `is_asserted: true`. A cursor becomes stale when the proposal store, manifest, request, or canon join changes.

Missing, unreadable, or inconsistent stores fail with explicit error codes rather than an empty page. The index is in memory, cached by proposal-file identity and metadata, and built with a deadline. Search has a separate deadline and returns no partial page. Logs contain only operation metadata, counts, duration, and error code.
